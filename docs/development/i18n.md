# Translation Contributor Guide

This guide documents how CHIVE handles user-facing text and how to add or
update translations.

| Field | Value |
|---|---|
| Audience | Contributors adding or changing user-facing strings. |
| Source of truth | Locale file roles, message key conventions, placeholder rules, and i18n parity expectations. |
| Update when | Supported locales, translation files, i18n service behavior, message key patterns, or parity checks change. |

## Supported Locales

Translation files live in `src/i18n/`:

| File | Purpose |
|---|---|
| `en.json` | English interface strings. |
| `pt-BR.json` | Brazilian Portuguese interface strings. |
| `qqq.json` | Message documentation for translators and reviewers. |

English is the source locale for new strings. Keep every non-metadata key in
all three files so locale switching never falls back to raw message keys and
translator context stays complete.

## Message Keys

Use `chive-` as the prefix for every application message key. Group related
keys by feature where possible:

- `chive-preset-*` for bundled sample dataset UI.
- `chive-chart-control-*` for chart control labels.
- `chive-chart-empty-*` for chart empty states.
- `chive-panel-*` for dashboard panel UI.

Choose stable keys that describe the UI concept, not the current English text.
For example, prefer `chive-chart-control-line-x` over a key that repeats the
visible label.

## Adding A String

1. Add the English text to `src/i18n/en.json`.
2. Add the Brazilian Portuguese translation to `src/i18n/pt-BR.json`.
3. Add translator context to `src/i18n/qqq.json`.
4. Use the key from code or markup through an existing translation path.
5. Run the i18n parity test before opening a PR.

Use `t('chive-message-key')` from `src/services/i18nService.js` for dynamic
JavaScript-rendered text. Static HTML can use `data-i18n` for text content and
`data-i18n-title` for title or aria-label text.

For static strings that intentionally contain trusted markup, add
`data-i18n-html` next to `data-i18n`. Translation files are project-controlled;
do not route user input through this path.

## Placeholders And Plurals

CHIVE uses banana-i18n positional placeholders:

```json
"chive-file-meta": "$1 rows · $2 columns · $3"
```

Pass values in the same order from JavaScript:

```js
t('chive-file-meta', rowCount, columnCount, sizeLabel);
```

When translating, preserve placeholder numbers and keep the meaning of each
placeholder compatible across locales. Reordering placeholders is allowed when
the target language needs it, but do not change what `$1`, `$2`, or later
positions refer to.

Plural messages use banana-i18n plural syntax:

```json
"chive-files-loaded": "{{PLURAL:$1|$1 file loaded|$1 files loaded}}"
```

Document placeholder meanings in `qqq.json`, especially for messages with
multiple values or plural forms.

## Runtime Behavior

`src/services/i18nService.js` loads the `en` and `pt-BR` message bundles at
module import time. On startup, `initializeI18n()` reads the saved locale from
`localStorage` key `chive-locale`; invalid or missing values fall back to
`pt-BR`.

The user-facing language control lives in the settings dialog opened from the
header settings button (`settingsController.js` + `settingsDialog.js`); it
calls `setLocale(locale)`. The i18n service owns no header widgets, only
locale validation, persistence, static retranslation, `<html lang>`, and the
locale-change event.

When `setLocale(locale)` runs, it:

1. Switches the banana-i18n locale.
2. Updates `<html lang>`.
3. Persists the selected locale.
4. Retranslates static `[data-i18n]` and `[data-i18n-title]` elements.
5. Dispatches `chive-locale-changed` so dynamic views can re-render.

Dynamic UI code that stores rendered labels should listen for the locale-change
event or be refreshed by an existing controller that already listens.

## Review Checklist

- Every new user-facing string has keys in `en.json`, `pt-BR.json`, and
  `qqq.json`.
- Locale files have the same non-metadata key set.
- `qqq.json` explains where the message appears and what placeholders mean.
- Placeholder numbers and plural forms are preserved across locales.
- Dynamic text uses `t(...)`; static markup uses `data-i18n` or
  `data-i18n-title`.
- Raw English or Portuguese strings are not added to JS/HTML where translation
  is expected.
- `npm test -- tests/i18n.keyParity.test.js` passes.
